## Runtime components

### Mobile application

`apps/mobile` is a React Native application built with Expo and strict TypeScript. Feature
code is co-located under `apps/mobile/src/features`; shared UI and visual tokens live under
`src/components` and `src/theme`.

The project uses Expo's managed/prebuild workflow and development builds because PowerSync,
op-sqlite, widgets, notifications, camera, and OCR require native modules. Native project
directories may be generated by Expo tooling, but product features must not be implemented
as hand-maintained Swift, Objective-C, Java, or Kotlin.

At untrusted data boundaries, the app validates domain objects with Zod schemas imported
from `@breadbox/core`. `packages/core/src/schema.ts` is the canonical `PantryItem` shape.

### Local database and sync client

The device database is PowerSync on SQLite via `@powersync/op-sqlite` and
`@op-engineering/op-sqlite` (ADR-010). Normal feature reads and writes target this local
database, so the primary pantry, shopping, favorites, activity, and announcement workflows
continue without a network connection.

PowerSync has two distinct directions:

1. **Download:** PowerSync Cloud replicates allowed Postgres rows and applies them to local
   SQLite automatically.
2. **Upload:** local mutations enter PowerSync's CRUD queue. The mobile connector sends that
   queue to `POST /sync/upload`; the API authenticates, authorizes, validates, and writes the
   changes to Postgres. Those committed changes then return through replication.

Signing out disconnects PowerSync and clears local data so one user's household data cannot
remain visible to the next session on the device.

### Synced data and tenancy

The client schema currently contains **10 synced tables across 4 PowerSync streams**:

| Stream | Scope | Tables |
|---|---|---|
| `household_members` | All memberships inside the signed-in user's households | `user_households` |
| `household_data` | Rows belonging to a household the user has joined | `pantry_items`, `households`, `shopping_list_items`, `favorite_recipes`, `activity_events`, `announcements`, `announcement_reactions` |
| `user_invites` | Invites created by the signed-in user | `household_invites` |
| `user_push_tokens` | Tokens owned by the signed-in user only | `push_tokens` |

Supabase access tokens are validated through JWKS. PowerSync exposes the JWT `sub` as
`auth.user_id()`; `infra/local-dev/sync-config.yaml` uses membership subqueries to prevent
cross-household downloads. The API independently enforces authenticated ownership and
household membership on writes. Push tokens are user-scoped and never stream to household
members.

`analytics_events` also exists in Postgres but is not part of the PowerSync client schema;
it is server-side product data rather than household state for offline use.

### API

`services/api` is a NestJS application deployed to Railway (ADR-009). To avoid a flag-day
rewrite, NestJS wraps an Express instance while legacy routers migrate incrementally.

Current authenticated endpoints:

| Method and path | Implementation | Responsibility |
|---|---|---|
| `POST /sync/upload` | Legacy Express | Drain and apply PowerSync CRUD entries |
| `POST /household/invite` | Legacy Express | Create a household invite |
| `POST /household/accept` | Legacy Express | Accept an invite and create membership |
| `POST /recipes/search` | Legacy Express | Validate, rate-limit, and proxy recipe search |
| `DELETE /account` | NestJS | Delete the authenticated account and associated data |
| `GET /recipes/:id/instructions` | NestJS | Backfill recipe instructions for detail/cook flows |

`GET /health` is an unauthenticated liveness probe. New endpoints are NestJS-first; legacy
routers keep their tested wire contracts until migrated. A scheduled, idempotent sweep sends
shopping-runner summaries, using Postgres state to tolerate restarts and multiple instances.

The API connects to Supabase through the session-mode Supavisor pooler. It also owns all
true partner secrets, privileged Supabase operations, input validation, rate limiting, push
fan-out, and server-side Sentry reporting.

### Production services

The active production topology is fully managed:

- **Supabase:** Postgres and Auth. The direct IPv4-enabled database endpoint supports
  PowerSync logical replication; the session-mode pooler serves the API.
- **PowerSync Cloud:** derives the offline sync service from Postgres and applies the
  repository's sync rules.
- **Railway:** builds and runs `services/api`.

The local equivalent under `infra/local-dev` uses Docker Compose with a source Postgres,
PowerSync's storage Postgres, PowerSync, and the API. `infra/azure` is parked reference IaC,
not an active deployment path.

## Data ownership and durability

Supabase Postgres is the durable server source of truth. PowerSync Cloud is a derived sync
replica, the API is stateless, and mobile SQLite is an offline working copy with queued local
mutations. In normal feature code, however, the **local database is the immediate source of
truth for the UI**: the app does not block a user action on a server round trip.

Database schema changes are represented in both places:

- fresh environments: `infra/local-dev/docker/modules/database-postgres/init-scripts`
- existing environments: numbered, idempotent files under `.../migrations`

Every schema change requires both a fresh-install baseline update and a matching migration.
The PowerSync client schema and sync rules must change in lockstep when replicated columns or
tables change.

## Conflict behavior and known debt

Most replicated mutable rows carry `updated_at` plus a soft-delete tombstone. The current
production-shaped `pantry_items` table has one UUID primary-key row per item and one quantity
field. Competing updates therefore resolve through the current last-write-wins behavior.

Quantity semantics require special care because three statements are materially different:

| Policy | Status |
|---|---|
| Naively sum concurrent writes | Rejected; replay is not idempotent |
| Per-device contributions merged with `max` | Required target invariant |
| Single-row `quantity` selected by `updated_at` | Current implementation (LWW) |

The required max-merge model is **not implemented**. ADR-011 is proposed implementation debt,
not a claim about current behavior. Correcting it requires a production migration and
backfill, mixed-version client support, API/upload changes, sync-rule changes, and torture
tests. No feature should introduce ad hoc summing or describe current writes as max-merge.

## Security boundaries

- Public mobile configuration uses `EXPO_PUBLIC_*`; it is extractable from the app bundle.
- Postgres credentials, Supabase service-role credentials, replication passwords, and
  partner API keys remain server-side.
- Sync-rule filtering protects downloads; API authorization protects uploads. Both are
  required—neither substitutes for the other.
- Household ownership is determined from authenticated membership, not client-provided
  identity fields alone.
- Soft deletes propagate tombstones to offline clients instead of silently removing rows.

See [`SECRETS.md`](SECRETS.md) and [`BACKUP-DR.md`](BACKUP-DR.md) for operational controls.

## Observability and validation

- Mobile and API errors are reported to Sentry when configured.
- Mobile product events use PostHog through the observability wrapper rather than direct
  feature-level vendor calls.
- Pure domain rules live in `packages/core` and are covered with Vitest.
- Mobile logic/components use Jest; API routes and modules use Vitest and Supertest.
- CI typechecks mobile and API, lints the repository, and runs all three workspace suites.
- Maestro flows under `.maestro` provide device-level smoke coverage.
