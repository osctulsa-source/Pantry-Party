## Verdict

The foundation is genuinely strong: the offline-first architecture is implemented
correctly (not just documented), the upload API is hardened well beyond typical

## P0 — Critical (fix now)

### 1. `DELETE /account` is broken against real Postgres — store-gate blocker

`services/api/src/modules/account/account.controller.ts` (step 3):

```sql
UPDATE household_invites SET used_at = NOW(), used_by = 'deleted' WHERE created_by = $1 ...
```

`household_invites.used_by` is **UUID** (`init-scripts/02-household-invites.sql`).
The literal `'deleted'` fails UUID coercion **at query parse time** — so this throws
on every call regardless of whether any rows match, the whole cascade rolls back,
and the endpoint 500s for every user. Account deletion is a hard App Store / Play
requirement.

It slipped through because `account.test.ts` mocks `pg` at the driver level — the
SQL string is never parsed by a real database.

**Fix:** drop the sentinel (`SET used_at = NOW()` alone, or `used_by = NULL`).
**Systemic fix:** see P1-#4 (integration tests against real Postgres).

### 2. Write-side tenancy gap on `/sync/upload` PUT path (IDOR)

`validateCrudEntry` in `services/api/src/routes/upload.ts` enforces only that
`added_by` / `created_by` / `user_id` equals the JWT sub. It does **not** verify the
caller belongs to the `household_id` being written:

- A crafted client can PUT a `user_households` row joining **any** household UUID —
  with `role: 'owner'`. The legitimate invite flow (`/household/accept`, which is
  well-guarded) is bypassed entirely.
- Data-table PUTs (`pantry_items`, `shopping_list_items`, `favorite_recipes`,
  `activity_events`, `announcements`, `announcement_reactions`) accept any
  `household_id` — the PATCH path checks membership by reading the row; the PUT
  (insert/upsert) path never does.

Household UUIDs are unguessable but not secret (they appear in analytics, logs,
push `data` payloads, co-member devices). With RLS intentionally off, this API is
the only write boundary — the gap is real, not theoretical.

**Fix:** in the upload transaction, for any PUT carrying `household_id`, verify
membership (`SELECT 1 FROM user_households WHERE user_id=$1 AND household_id=$2`)
before the upsert — mirroring the PATCH path. For `user_households` PUTs, only
permit the bootstrap case (the referenced household's `created_by` = caller and the
household row is new in the same batch), or move bootstrap to a dedicated
`/household/bootstrap` endpoint and reject membership PUTs outright.

## P1 — High (fix before public launch)

### 3. Account-deletion cascade leaves personal data behind

The cascade tombstones pantry/shopping items and revokes invites, but misses:
`activity_events`, `announcements`, `announcement_reactions`, `favorite_recipes`
(rows keep the deleted user's id as attribution) and — most visibly —
`push_tokens`, which are user-scoped and stay `deleted = FALSE`, so a deleted
user's devices **keep receiving household pushes**. Extend the cascade (tombstone
attribution rows, hard-delete or tombstone push tokens).

### 4. No integration tests against a real database

Every API test mocks `pg` at the driver boundary. SQL/DDL drift (types, CHECK
constraints, constraint names) is never exercised — P0-#1 is the proof. Add a CI
job with a Postgres service container that applies `init-scripts` + numbered
migrations and runs a small set of wire tests (upload round-trip per table,
account cascade, invite accept). The local-dev compose stack already provides the
schema; `testcontainers` or a GHA `services:` postgres both work.

### 5. ~40 modified files uncommitted (+ untracked artifacts)

Core sync files, API routes, tests, and docs are modified in the working tree but
not committed; untracked items include `RootErrorBoundary.tsx`, several
`*-preview.html` files at repo root, PostHog setup reports, and
`data/recipes/_validate-out.txt`. Risks: CI hasn't gated this state (tests pass
today — verified above — but nothing protects it), work can be lost, and
`publish-ota.sh` correctly refuses a dirty tree, so OTA is currently blocked.
Commit or deliberately stash; move preview/report artifacts out of the repo root
(or gitignore them).

### 6. No staging environment — dev builds run against production

All three `eas.json` profiles (`development` included) point at the **production**
PowerSync instance, Railway API, and Supabase project. Everyday dev and testing
writes land in the production database, and a destructive bug in a dev build
reaches real data. Before traction: staging Supabase project + PowerSync instance
+ Railway service, pointed to by the `development`/`preview` profiles.

### 7. Rate limiting and caches are single-instance only

`FixedWindowRateLimiter` and `TtlCache` (`services/api/src/lib/`) are in-process.
Correct at one Railway instance; quotas silently multiply at 2+ replicas. Either
pin/document the single-instance invariant (Railway replicas = 1) or back the
limiter with Redis/Postgres. Also: the runner-summary sweep claims multi-instance
safety, but it stamps `runner_summary_sent_at` **after** sending — two instances
can both send within the race window. Claim first with
`UPDATE ... SET runner_summary_sent_at = NOW() WHERE id = $1 AND runner_summary_sent_at IS NULL`
and send only when `rowCount = 1`.

## P2 — Medium (growth hardening)

### 8. `services/api/Dockerfile` production readiness

- Build context is `services/api` only, so the root `package-lock.json` is absent
  and the image runs `npm install` — **unpinned, can drift from CI-tested deps**.
- Ships devDependencies and runs via `tsx` (no compiled `dist/`); slower cold
  start, larger image, broader surface.
- Runs as root; `ENV NODE_ENV=development` is baked in (Railway's env overrides it
  to `production`, but the image default is wrong).

Fix: multi-stage build (copy root lockfile, `npm ci`, `tsc` build, prune), run
`node dist/main.js` as `USER node`, `NODE_ENV=production`.

### 9. Production migrations are manual + docs disagree

Prod schema changes are applied by hand via `psql` from a dev machine. Meanwhile
`migrations/README.md` says there is **no** `schema_migrations` ledger, while
`infra/managed/README.md` and `BACKUP-DR.md` describe using one — and the managed
README is stale ("7 tables", init-scripts 00–06) vs. the repo's 10 synced tables +
`analytics_events` (init-scripts 00–08, migrations 0001–0009). Unify on one
documented runner (the `infra/azure/migrations/run.sh` ledger model is good —
it's parked, not dead), apply it in CI or as a documented pre-deploy step, and
refresh the table counts.

### 10. Theme-token violations (brand-decoupling rule)

Hardcoded hex in feature code, despite the "never hardcode a color" invariant:

- `'#FFFFFF'` chip text (`ScanScreen`, `DeleteAccountScreen`) and `'#F6F2E9'`
  header text (`RecipeDetailScreen`, `RecipesScreen`) — these are the **light**
  `onAccent` values; in dark mode (`onAccent: '#18140E'`) contrast breaks.
- `'#E0B85A'` accents in `CollectionsScreen`.
- `RootErrorBoundary.tsx` (untracked) duplicates the light palette literally.
- `collectionIcons.tsx` carries a large fixed illustration palette — artwork is a
  gray zone, but it will not adapt to dark mode.

Fix: route through `tokens`, add an ESLint rule banning hex literals outside
`src/theme/**` (with an explicit allow-list for illustration art), and decide on
`RootErrorBoundary` (commit it — a root boundary is worth having — using tokens,
or delete it).

### 11. Dead code & stale scaffolding

- `src/data/stubPantry.ts` and `src/data/powerSyncPantry.ts` import only each
  other; nothing references them (features use `usePantryItems`). Delete.
- Root `app.json` (`{"expo": {}}`) — scaffold leftover; remove or document.
- `apps/mobile/package.json` `//` comment still says "Phase 1: add the chosen sync
  engine (PowerSync…)" — PowerSync is integrated; update the comment.
- Root `npm test` is an `echo` no-op — a contributor can believe tests ran when
  none did. Aggregate the workspace suites or fail loudly.

### 12. Dependency hygiene

- `lucide-react-native: "latest"` in `apps/mobile` — unpinned; breaks reproducible
  installs. Pin it.
- `journeyapps/powersync-service:latest` in local compose — pin a version.
- No Dependabot/Renovate config — update cadence is fully manual.

### 13. Auth/PowerSync lifecycle edge cases

- `onAuthStateChange` fires on token refreshes too, so `ensureDefaultHousehold()`
  re-runs on every refresh (harmless, wasteful). Gate on `SIGNED_IN` /
  `SIGNED_OUT` events only.
- Race: sign-out before `connect()` completes leaves `_connected = false`, so
  `disconnectAndClear` no-ops while a connect is in flight — the next user on the
  device could briefly see the previous user's local data. Serialize
  connect/disconnect through a single promise chain.

## What's genuinely good (keep doing)

- **Docs as an asset:** ARCHITECTURE/DECISIONS/SECRETS/BACKUP-DR are accurate,
  current, and unusually honest (ADR-011 states "not implemented" in bold). The
  dual init-script + migration lockstep rule is written down and followed.
- **Upload API hardening:** zod at the boundary, table/column allowlists,
  parameterized SQL, loud 400s on immutable-column edits, TOCTOU guards on invite
  accept, idempotent upserts, batched transactions, server-only columns
  (`runner_summary_sent_at`) deliberately excluded from client writes.
- **Offline-first done right:** local-first reads/writes, tombstones, correct
  household scoping in sync rules, sign-out wipes local SQLite, bootstrap waits
  for first sync.
- **Secrets posture:** no privileged secrets in git (verified by scan); the
  `EXPO_PUBLIC_` boundary is documented and respected; Spoonacular key is
  server-side with rate limiting + caching + graceful 503.
- **Privacy-aware telemetry:** PostHog identify by user-id only, Sentry strips
  user info/bodies, telemetry wrapped so it can never break a user flow.
- **Testing culture:** 556 tests, pure domain logic in `packages/core` heavily
  covered, wire tests for API contracts, Maestro smoke flows, OTA publish script
  encoding lessons from past incidents.
